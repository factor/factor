# Native x86 compiler feature evidence

The four optional transformations execute and preserve the checked outputs. The constructed representation witness has a substantial measured speedup, and integer SLP has a smaller repeatable speedup. LICM and memory reuse reduce their witnesses' retired instructions but increase CPU time in these observations. The existing 26-workload corpus shows no broad improvement that supports enabling all four by default. No defaults or production files were changed by this measurement work.

[MEASUREMENTS.md](MEASUREMENTS.md) gives the aggregate and individual-round tables. [results.json](results.json) retains every case, compiler observation, static report and ratio. Its strict collector accepted five checked configurations and ten timing processes, totaling 900 measured batches. There were no failed, retried or discarded timing processes.

## Important limits and controls

The shared order is OFF, LICM, representation, memory, SLP / SLP, memory, representation, LICM, OFF. Both OFF anchors are reused across comparisons, so estimated effects are correlated and have different temporal spacing. Three measured batches per case per process yield six runtime samples per setting, but only two independent process observations and two compiler observations. These data do not establish statistical significance.

LICM's witness retires approximately 500,015,490 instructions per batch instead of 700,015,470, consistent with two loop instructions removed over 100,000,010 iterations. Its CPU time increases in both rounds: +54.646% and +52.596%. The **unchanged loop witness under representation-only mode** is an important control: retired instructions remain unchanged, while CPU changes +55.093% in round1 and −1.082% in round2. Thus the observed CPU behavior cannot be attributed solely to LICM's semantic transformation. Code placement or execution-state sensitivity is a hypothesis, not an established cause.

A separate untimed installed-code capture ran only after all timing finished. It compiled the actual typed loop and dynamic WORK under OFF, LICM-only and representation-only, then executed the independent oracle. [Disassembly and metadata](audits/loop-code/summary.json) show 96-byte code allocations in all states. The OFF backward loop begins at offset43 with seven static instructions through its backward branch; LICM begins at46 with five. In this detached capture all entry addresses were mod64=48, with loop labels mod64=27/30/27. OFF and representation-only code differ only in the three RIP-relative safepoint-store relocation displacements; their decoded operations and safepoint target address match. These are **not the addresses of the exited timing processes**, and the static disassembly is not a hardware branch trace. It does not resolve the CPU regression.

SLP's constructed mixing witness improves retired work by 2.669% and CPU by 3.132%, despite its native code allocation growing from224 to240 bytes. Its original-corpus retired geomean instead regresses 0.132%, dominated by Base32's repeatable +3.419% retired / +3.219% CPU. The earlier unrelated GVN/rematerialization matrix had a similar Base32 delta; the cause is unresolved here, and these records do not prove that a vectorized Base32 path caused it.

Memory reuse removes three final IR instructions from its witness (103→100, code allocation496 bytes unchanged), but witness CPU rises 5.525%/2.422% across rounds. Existing msgpack, CSV, JSON and Base32 show small retired-work reductions, often with higher CPU. Representation reduces its witness's code2496→2448 bytes and spills/reloads26→24; its strong targeted improvement is separate from the original corpus's near-flat retired result. Scalar nbody code grows2960→2992 bytes. Compiler work measures the entire selected closure under each flag, not an isolated per-pass timer.
